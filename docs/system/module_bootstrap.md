# Module Bootstrap ABI Version 1

The [asynchronous module lifecycle](../modules/asynchronous_module_lifecycle.md)
is the implemented Host orchestration around this ABI. The Host I/O worker loads,
binds, installs and unloads DLLs; per-thread preparation still runs on each new
module thread. The Host starts its workers before asynchronously bootstrapping
the Executive. The installation ordering below includes the shared sequence counter.

Shared binding contracts and installation support live in `framework/module/`.
`host/module/bound_module.*` owns the binding and native module lifetime;
Foundation's `foundation/platform/module/binding.*` supplies the reusable native loader.

The current pre-release ABI retains the nine-function core table, including
installation of the Host-owned shared sequence counter. The common endpoint
refactor resets the affected bootstrap contract to version 1; the Host and all
modules must be rebuilt together. The exported entry point is
`morphic_module_bootstrap_v1`. Host and module exchange the same
`SAdvertisedIdentity` representation: claimed module ID, version, and inclusive
functional-major range. No compatibility adapter is retained; all components
are rebuilt together.

`advertised_module_id` is deliberately named as such even within the advertised
identity structure: it is the component's claim and is distinct from the
ambient module identity assigned and installed later for execution.

The functional-major range describes the shared bootstrap/core protocol majors
with which each participant can interoperate. Binding requires the two ranges
to overlap and negotiates the highest common major. That selected major governs
the core function table and subsequent function queries. Host, module, and
functional majors are currently all 1.

The executive validates and installs its immutable local-type table and its
component-local erased-owner operation authority before returning bootstrap
functions. That authority combines a SYSTEM table compiled into the DLL with
the DLL's own LOCAL table. The host then exchanges numeric advertised
identities, populates the version-1 core surface, and installs services in this
order:

1. host-owned system-registry view;
2. ambient module identity;
3. module memory context;
4. shared sequence counter;
5. debug service.

The SYSTEM table is generated by Framework's
`system/system_erased_owner_operations.cpp`, compiled once into each participating
binary through its shared source import. Foundation supplies the generic operation
registry; component-local generators remain separate. This separation does not
change catalogue ordinals, bootstrap ABI or installation order.

The module memory context is component-specific: its system identity must belong
to the installed ambient module. The host and executive contexts may share an
allocator, but they remain distinct attribution authorities with independent
live-allocation and byte counters. A context must be empty when installed.

Only after all five services, the advertised peer identity, negotiated
functional major, local type table, and erased-owner operation authority are
installed is the module ready for function queries or thread setup.
Thread identity, provisioning, and thread memory are installed later on each
created module thread.

`foundation/system/system_context.hpp` exposes
`system_context::sequence_counter`, a module-local public
`std::atomic<std::uint64_t>*`. It is null before installation. The Host owns the
atomic in static storage, initialised to zero for process lifetime, and installs
that same address into every module before any module work starts. Installation
rejects null and repeated installation; it neither reads nor resets the counter.
Module reloads and Host context recreation do not reset it. The pointer is fixed
while module work runs and must not be reassigned by consumers.

Claim a sequence number using:

```cpp
const std::uint64_t sequence =
    system_context::sequence_counter->fetch_add(1u, std::memory_order_relaxed);
```

The returned value is the previous value, so the first claim returns zero.
Claims share the atomic's modification order across threads and modules. Values
increase modulo 2^64 and wrap from `UINT64_MAX` to zero; zero is a valid sequence
number. Callers must use comparisons appropriate to their wraparound window
instead of assuming ordinary numeric ordering across a wrap. This counter only
orders sequence claims: it does not publish associated data or order completion
of the work carrying a sequence number. Existing transports or other explicit
synchronisation must provide data visibility. Consumers may load or increment
the atomic, but must not store/reset it during use.

`host/threading/CThreadPackage` owns the native thread, launch configuration,
prepare callback/context, batch-client instance and notification/execution pins.
Its trampoline receives the Host package and constructs a
`framework/threading/CThreadContext` before preparation. Preparation installs that
exact context pointer; the requested entry receives the context by reference.
The module's `is_thread_context_ready()` check validates that installed pointer.
Shared endpoint resources contain assigned identities, performance conversion,
wait/control state and message channels, with borrowed batch-client and Host
execution access; they do not contain the native thread or launch callbacks.
Host supplies the owner and worker endpoint identities when creating them.

`framework/threading/CEndpointContext` exposes common lifecycle, identity,
batch-client and message operations to pumps and requested threads.
`CThreadContext` adds native-thread waiting. Terminal publication, native join,
late notification/batch-publisher quiescence and final resource/pin release
remain separate steps. A terminal state or completed join alone does not permit
releasing resources still reachable by publishers.

Before registry installation, name lookup is unresolved and diagnostic paths
use numeric fallback. Any bootstrap failure leaves the module non-ready and
the host unloads it without starting module work.

Operation authority is installed once and has no uninstall path. Its function
pointers remain in component-local static storage and are not part of the
bootstrap ABI exchanged with the host. During ordinary shutdown the module pump
orders child stops. Host joins returned native executions and drains their final
submissions; endpoint transports and pins remain until accepted work and all
publishers are quiescent. Accepted asset operations are drained; any retained assets still
flagging a dependency on the outgoing module trigger an assertion log and are
disposed of before unbinding. The host then requires the module context's allocation count and
attributed bytes both to be zero before native unload. A failed audit leaves the
DLL loaded, preserving its code and component-local operation authority.
Consequently all LOCAL owners are gone before their defining DLL and operation
authority become unavailable.
The system registry view points to immutable host static storage and remains
valid for host lifetime, including while queued host-owned debug records drain.
No local identity is transported in this phase.
